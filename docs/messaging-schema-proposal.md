# Private conversations: schema proposal

**Status: approved October 17, 2026, and merged in PR #10.** Backend implementation follows this design; see [messaging](messaging.md) for the contract, tests, and deployment status. The iPhone messaging UI remains a separate PR.

## Scope

One private text conversation per mutually connected pair. Existing reciprocal `connect` decisions remain the source of connection status; there is no new matches table. Conversations are created when an eligible participant first opens chat, so existing connections need no backfill.

The first implementation PR will provide schema, authorization functions, an authenticated messaging endpoint, and database/handler tests. The following PR will add Swift core models, an SDK adapter, and conversation UI. Attachments, group chats, message editing/deletion, read receipts, notifications, and live subscriptions are outside this increment.

## Proposed tables

Both tables live in the non-exposed `private` schema. All columns below are required.

| Table | Column | Purpose |
| --- | --- | --- |
| `conversations` | `id uuid` | Server-generated primary key |
| | `participant_one_id uuid` | Foreign key to `public.profiles(id)` |
| | `participant_two_id uuid` | Foreign key to `public.profiles(id)` |
| | `created_at timestamptz` | Database-generated creation time |
| | `last_activity_at timestamptz` | Initially creation time; advanced atomically when a new message is inserted |
| `messages` | `id uuid` | Server-generated primary key |
| | `conversation_id uuid` | Foreign key to `private.conversations(id)` |
| | `sender_id uuid` | Foreign key to `public.profiles(id)`; supplied by verified Auth identity |
| | `client_message_id uuid` | Stable retry identifier generated by the app for each send |
| | `body text` | Plain text, 1–2,000 Unicode code points; reject whitespace-only text |
| | `created_at timestamptz` | Database-generated send time |

Store the two participant UUIDs in ascending order. A check constraint requires `participant_one_id < participant_two_id`; a unique constraint on that pair prevents self-conversations and duplicate threads, including simultaneous opens.

Unique `(conversation_id, sender_id, client_message_id)` prevents duplicate sends after a timeout. An identical retry returns the original message. Reusing the key with different text returns a conflict, never overwrites the original. Authorization is checked again before returning a retried message. Sender and conversation membership are validated together inside the send function; this cross-table rule does not belong in a SQL check constraint.

Messages and conversation membership are immutable in this increment. Only the server send function advances `last_activity_at`, in the same transaction as a new message; retries do not bump it. No client-supplied creation timestamps, mutable participant lists, or cached copies of email, birthday, selfie, or profile details are stored here.

## Authorization

The authenticated Edge Function resolves the caller through Auth, following discovery's existing pattern. Request bodies cannot select the sender or caller. Bounded commands are `list`, `open`, `history`, and `send`; `open` accepts the other profile ID and `history`/`send` accept a conversation ID. Every database function independently validates that the verified caller belongs to the requested conversation and that the pair is still allowed.

Use `private.discovery_pair_allowed` plus reciprocal `connect` decisions on every read, open, and send. Do not infer permission from possession of a conversation UUID or from the client displaying a connection. Unauthorized and nonexistent threads produce the same unavailable response without disclosing membership or message contents.

Enable RLS on both tables and explicitly revoke all direct table privileges from `PUBLIC`, `anon`, and `authenticated`. There are no client table policies/grants and no direct Realtime publication. Grant the server role only the operations needed by the server functions, including column-limited updates to conversation activity. Public RPC entry points use `SECURITY INVOKER`, an empty search path, fully qualified names, and server-only execution grants; internal helpers remain in `private`.

The server role bypasses RLS. Consequently, **function authorization checks and verified caller injection are essential**; RLS/default-deny grants protect direct client access, not mistakes in server functions. Test both boundaries. This follows the existing discovery model without adding broadly executable `SECURITY DEFINER` helpers.

## Approved behavior

| Event | Proposed behavior |
| --- | --- |
| One-sided check or pass | Cannot open, read, or send a conversation |
| Either participant hides their profile | Pause access for both people; retain messages; resume when both are eligible again |
| Either participant loses photo/review eligibility or is suspended/rejected | Pause access for both; retain messages |
| Either participant blocks the other | Immediately deny subsequent reads/sends in both directions; retain stored history for now |
| Either participant deletes their account | Delete the conversation and its entire message history for both people |

The hide/photo behavior deliberately matches current Connections eligibility. Keeping established chats usable while hidden is a reasonable alternative, but would require a separate messaging eligibility rule rather than reusing discovery's rule.

Deletion uses `ON DELETE CASCADE` from either participant profile to the conversation and from the conversation to all messages; sender references also cascade. There are no message files to clean up. Provider backup retention remains separate. No moderation evidence archive or automatic message expiry is added; those require an explicit retention design before the broader rollout.

Blocking and sending must acquire the same transaction-scoped lock for the canonical pair and recheck authorization after taking it. Extend the existing block function to use that lock. This orders concurrent block/send operations: once a block commits, a later send cannot succeed. An earlier read or already downloaded message cannot be recalled. Requests after a committed visibility/eligibility change must also fail authorization.

## Queries and indexes

- Keep the pair uniqueness index for duplicate prevention. Add `(participant_one_id, last_activity_at DESC, id DESC)` and the equivalent second-participant index for inbox queries and foreign-key cleanup.
- Index messages on `(conversation_id, created_at DESC, id DESC)` for history and last-message lookup. Add a sender index for foreign-key cleanup.
- Return at most 50 conversations per page, ordered by `(last_activity_at DESC, id DESC)`, and at most 50 messages per history page, using `(created_at, id)` cursors. Validate cursor types and ownership. History initially returns the newest page; the UI can reverse it for display.
- Derive the last-message preview through the history index rather than storing a second copy of its body. New sends can move an inbox row between pages; the UI must deduplicate conversation IDs and refresh the first page to reconcile activity.

The use of UUID tie-breakers gives deterministic ordering when timestamps match. Explicit response projections contain only the authorized thread, its public participant summary, and the requested messages. Any profile-photo links use the existing profile-only signer; no private profile rows are returned. Responses are `no-store`, and logs omit message bodies and credentials.

## Implementation and test plan

1. Create a migration through the Supabase CLI; add private tables, constraints, indexes, grants, functions, and the shared block/send lock. Follow the documented local/hosted migration-history mismatch before deployment.
2. Add SQL tests for anonymous/direct access denial, unrelated and forged callers, one-sided interest, mutual access, hidden/ineligible/blocked pairs, duplicate opens, safe send retries, changed-body conflicts, validation, cursor paging, and account-deletion cascade. Add a two-session concurrency test for simultaneous open and block/send ordering.
3. Add `supabase/functions/messaging/{index.ts,handler.ts}` with injected transport and handler tests for Auth, caller injection, bounded input, sanitized failures, and explicit output fields. Extract shared Auth/HTTP helpers only where the third endpoint makes duplication concrete.
4. Include the messaging suites in CI; run local database checks and advisors before requesting implementation review. Provide device acceptance steps for the UI PR. Review the backend implementation separately from the approved design and the subsequent iPhone UI.
