# UI and messaging iteration plan

Status: proposed October 21, 2026. Each item below is one focused implementation PR; check it off and add its PR URL when merged. No schema or deployed behavior changes are included in this plan.

Target bottom navigation: **Profile · Discovery · Connections · Messages**. Profile gets Preferences immediately left of Settings at the top right. Preferences arrives with its working age screen, rather than a placeholder button.

## PR checklist

- [ ] **PR 1 — Limit new messages to 500 characters.** Preserve the owner's existing local edits in `MessageText.maximumLength` and the composer. Update client validation, server command validation, and database send enforcement with a new forward migration; do not edit a deployed migration. Generate limit text from the constant to prevent drift. Keep existing messages up to the previous 2,000-character limit readable and preserve idempotent retries of previously accepted messages. Do not truncate stored history. Test exactly 500/501 Unicode code points, whitespace, emoji, old-message reads and old-send retries. Existing core tests still expect 2,000 and must be updated. Deploy the compatible backend before distributing the client; older clients may receive a validation error when sending over 500.
- [ ] **PR 2 — Move Settings into the profile toolbar.** Remove the Settings tab and add an accessible cog at the top right of Profile. Push the existing settings screen within Profile's navigation stack. Keep Personal info, visibility, sign-out, account deletion, and their state handling intact. Keep account lifecycle actions in the signed-in shell. Verify back navigation, accessibility labels, sign-out/account switching, and deletion confirmation.
- [ ] **PR 3 — Give Connections its own bottom tab.** Extract the connections list from `DiscoveryView` into `App/Features/Connections`. Remove the Discover/Connections segmented picker. Keep Discovery focused on browsing/check/pass; Messages stays its own tab. Reuse profile cards and the existing discovery service contract rather than duplicating transport code. Explicitly refresh on tab activation/foreground/pull and after relevant mutations; do not rely on a hidden view's task to refresh another screen. Test loading/empty/error states, refresh cancellation, Message navigation, and blocking from Connections.
- [ ] **PR 4 — Move started conversations from Connections into Messages.** Confirmed: transition after the first message sends successfully. Apply the chosen classification on the server so both participants and all devices agree. Preserve the underlying mutual connection; this is a list transition, not unmatching or deletion. Empty threads remain represented in Connections and appear in Messages only once a message is committed. Use the existing conversation/message relationship rather than introducing a redundant boolean. Keep history, discovery exclusions, blocking, and send authorization intact. Filter before ordering/limiting results. Refresh both lists after starting a conversation; ambiguous send responses must reconcile against server state. Test both accounts, concurrent opens/sends, failed sends, retries without duplicates, existing empty threads, and back navigation. Review the proposed query/migration changes before implementation.
- [ ] **PR 5 — Persist age preferences and filter discovery on the server.** Review schema and contract first. Proposed shape: owner ID, minimum age (18 or greater), nullable maximum age (no upper preference by default), and updated timestamp; maximum must be at least minimum. Prefer the existing discovery-settings storage if it remains a clear fit, otherwise a small owner-scoped preferences table. Keep exact date of birth private and filter candidates before pagination. Proposed behavior: the viewer's chosen range filters their discovery candidates; existing connections and messaging remain available. Do not add preference checks to shared pair authorization. Defaults must preserve current discovery for existing users. Use owner authorization/RLS as appropriate to the existing server-mediated access path. Test ownership, bounds/defaults, birthday boundaries, result ordering/limits, and unchanged existing conversations. No new SDK dependency is needed.
- [ ] **PR 6 — Add the profile Preferences control and age screen.** Add an accessible preferences/sliders icon immediately left of the cog. Implement a compact age-range editor with load/save/error states backed by PR 5. Display saved values and persist them across sign-out/in; clear account-specific state on account change. After a successful save, refresh discovery and remove candidates now outside the range. Keep save/cancel behavior explicit and preserve unsaved edits on recoverable failure. Test validation, persistence, navigation, account switching, and the visible change in discovery. Add model/service types only as their implementations arrive, under Core/Discovery and Supabase/Discovery (or a dedicated Preferences feature if responsibilities grow).

PRs 1–3 can be reviewed independently. PR 4 follows the Connections split. PR 5 precedes PR 6, and PR 6 uses the profile toolbar introduced in PR 2. Backend and client rollouts remain separate, documented steps; a merge does not automatically deploy either.

## Decisions to confirm

1. Confirmed: move into Messages after the first committed message, for both participants. Simply opening and closing a chat keeps the connection in Connections.
2. Proposed age behavior is a minimum/maximum range, defaults 18 to no upper limit, applied to the viewer's discovery feed only. Confirm before schema implementation. It does not reveal birthdays or disconnect existing matches.

## Code organization

`NewToTownCore` is a first-party local Swift package declared in the repository-root `Package.swift`. Xcode references the root directory (`relativePath = .`). The source is tracked under `Sources/NewToTownCore`, including `Messaging/MessagingService.swift`. It appears under Package Dependencies because that is how Xcode presents Swift package modules; it is not fetched from a separate repository.

Keep that boundary: SwiftUI presentation under `App/Features`, domain rules/state/service contracts under `Sources/NewToTownCore`, backend adapters under `Sources/NewToTownSupabase`, and corresponding tests in `Tests`. Supabase's SDK is the external package dependency. No directory-wide reshuffle, generic repository framework, or package removal is needed for these changes.
